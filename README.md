# IotExpertApp

Приложение для ЛР3 ИИСиТ: монитор ESP32 с записью и replay, прямой вывод по внешней БЗ из 20 правил ЛР1, ручная консультация в консоли и GUI с деревом объяснения, структурированный редактор правил с сохранением рабочей копии. Добавлена автоматическая оценка качества наблюдений через DeviceProfiles и прежнюю БЗ ЛР1; объяснение фиксирует выбранный снимок. Физическая диагностика и калибровка остаются отдельным предметным этапом.

## Запуск

Из каталога с IotExpertApp.csproj:

```bash
dotnet restore IotExpertApp.csproj
dotnet build IotExpertApp.csproj
dotnet run --project IotExpertApp.csproj
dotnet run --project IotExpertApp.csproj -- --self-test
dotnet run --project IotExpertApp.csproj -- --write-synthetic-sample synthetic-uart.log
dotnet run --project IotExpertApp.csproj -- --console --file synthetic-uart.log
```

Консоль с реальной платой:

```bash
dotnet run --project IotExpertApp.csproj -- --console --port /dev/cu.ИМЯ_ПОРТА
```

Имя заменить на обнаруженный порт; на Windows используется имя COM. Параметры: 115200, 8N1, без flow control. Serial monitor другой программы должен освободить порт. GUI и CLI одновременно один порт не открывают. DTR/RTS не используются для преднамеренного сброса; фактический reset при открытии обрабатывается как новый boot.

На Windows OutputType=Exe нужен для консольного режима; при запуске GUI может появляться консольное окно. Скрытие окна при сохранении полноценного CLI — отдельная упаковочная задача.

## Сборка с --no-restore

В текущем csproj пакет AvaloniaUI.DiagnosticsSupport исключен из assets вне Debug. Файл obj/project.assets.json общий для конфигураций, поэтому после Release-restore Debug-сборка с --no-restore может выдать CS1061 для WithDeveloperTools. Это не ошибка using: сначала нужно восстановить пакеты для выбранной конфигурации.

```bash
dotnet restore IotExpertApp.csproj -p:Configuration=Debug
dotnet build --no-restore --tl:off
```

Для Release:

```bash
dotnet restore IotExpertApp.csproj -p:Configuration=Release
dotnet build -c Release --no-restore --tl:off
```

При смене конфигурации повторить соответствующий restore либо использовать обычный dotnet build без --no-restore. Вызов WithDeveloperTools остается только под #if DEBUG; менять код или версии пакетов для этой ситуации не требуется.

## Работа

В GUI выбрать порт и подключиться либо указать абсолютный путь UART-записи. Остановить прием можно кнопкой. Файл читается быстро либо по времени с паузой; режим выбирается перед запуском. Путь выбирается текстовым полем; файловый диалог будет последующим улучшением.

Модели пакета и наблюдений не являются сущностями ORM. ObservationStore хранит один текущий снимок. TelemetryReceiverService координирует источник, сборку строк, парсер и хранилище. MainViewModel получает сервис через конструктор и обновляет свойства интерфейса на UI-потоке. App создает зависимости и останавливает прием перед закрытием окна.

Синтетическая запись создается только командой --write-synthetic-sample; это не измерения платы. --self-test проверяет части приемника на искусственных входах. Консольный приемник возвращает ненулевой код при ошибке формата, порядка, хвосте, ошибке источника или отсутствии валидных пакетов.

## Текущие ограничения

- Поддерживается schema_version=1 и профиль stand-v1-pir-unverified; несовместимые пакеты отклоняются с сообщением.
- Технические карточки показывают возраст на момент снимка; автоматическая live-оценка дополнительно учитывает монотонное время после приема.
- Последняя успешная величина не подменяет ошибку последней попытки.
- PIR не подтверждает движение, OLED не подтверждает картинку, SD — результат последнего стартового/выборочного теста, реле — GPIO без обратной связи контактов.
- local_diagnostic показывается как локальное заключение прошивки, не результат экспертной системы приложения.
- Есть контроль sequence/uptime и согласованности времен/счетчиков источников; он обнаруживает противоречия наблюдениям, а не физическую причину неисправности.
- Автоматический профиль связывает качество пяти источников с БЗ ЛР1 и фиксирует объяснение снимка; это ограниченный контроль получения данных. Полная v0.1.0 и универсальная диагностика устройства не завершены.

Полный объем версии: docs/codex/LR3_APP_v0.1.0_SPEC.md. Ожидаемые и фактически пройденные проверки разделяются в отчете Codex.



## Шаг 02: запись и воспроизведение

При подключении к UART можно указать новый абсолютный путь в поле записи. Пустое поле отключает запись. Существующие файлы не затираются. Записываются исходные байты до разбора: загрузочные логи, правильные и поврежденные JSON-строки. Заголовки, BOM и переводы строк от приложения не добавляются. Ошибка записи не прекращает прием и отображается отдельно.

Лимит одного файла — 10 МиБ. При нехватке места для очередного блока запись останавливается перед ним, а прием продолжается. Кнопка «Завершить запись» закрывает файл и не отключает порт. Файл может закончиться неполным кадром при остановке/лимите; хвост учитывается при replay, а не дополняется автоматически. Это запись доступного приложению потока, а не гарантия отсутствия потерь до UART-драйвера. Запись не обязана начинаться с sequence=0.

Новая команда для реального порта, имя заменить на подтвержденное имя ESP32:

```bash
dotnet run --project IotExpertApp.csproj -- --console --port /dev/cu.usbserial-0001 --record /АБСОЛЮТНЫЙ/НОВЫЙ/esp32-real.log --seconds 30
```

Каталог файла должен существовать. --seconds принимает от 1 до 300, после интервала выполняется штатный Stop. Без ограничения времени CLI завершается по Ctrl+C. GUI и CLI не открывают один порт одновременно.

```bash
dotnet run --project IotExpertApp.csproj -- --console --file /АБСОЛЮТНЫЙ/esp32-real.log
dotnet run --project IotExpertApp.csproj -- --console --file /АБСОЛЮТНЫЙ/esp32-real.log --timed
```

В GUI флажок «Воспроизводить по времени» применяется при запуске файла. Пауза/продолжение действуют только на replay. «Остановить» завершает чтение, повторное «Прочитать файл» начинает его сначала. Быстрый режим не делает ожиданий. Живой UART не ставится на паузу этой кнопкой.

Интервалы определяются uptime между принятыми пакетами одного запуска, а не датой компьютера. Первый пакет показывается сразу, новый boot начинает отдельную шкалу времени. Пауза замораживает часы записи; EOF не оставляет фонового отсчета. У текстовых строк нет собственного времени, они обрабатываются между соседними пакетами. Виртуальный uptime отображается отдельно; возраст в карточках по-прежнему указан на момент снимка. Вывод о годности данных и экспертные пороги здесь не добавлены.

Межпакетная проверка не допускает уменьшения времен/числа попыток и изменения values без нового времени успеха. При одной новой ошибке сохраняется прошлый успех. При нескольких попытках допускаются пропущенные промежуточные успехи/ошибки; при насыщении счетчика не предполагается точное число попыток. Несогласованный пакет не заменяет снимок и считается отдельно от ошибки JSON.

«Пропуски» означают промежуток между номерами принятых пакетов: причиной может быть как потеря, так и отклонение пакета валидатором. Счетчик не определяет физическую причину.

Проверки --self-test дополнены искусственными переходами наблюдений, точной записью байтов, запретом перезаписи, лимитом, паузой и остановкой replay. Они не являются проверкой физической ESP32. Фактические аппаратные результаты сохраняются отдельно в docs/codex/STEP_02_RESULT.md вместе с реальной записью.

## Шаг 03: техническое ядро внешней БЗ

Это проверка алгоритма по искусственным данным, не диагноз ESP32. Четыре правила SYN-* не входят в минимум двадцати предметных правил. На этапе 03 диалог, маппинг и GUI были отдельными задачами; их текущее состояние описано в разделах шагов 05–09.

```bash
dotnet run --project IotExpertApp.csproj -- --infer --knowledge KnowledgeExamples/synthetic-engine.json --facts KnowledgeExamples/synthetic-facts.json
dotnet run --project IotExpertApp.csproj -- --self-test
python3 docs/codex/checks/step03/verify_knowledge_cli.py
```

Последняя команда требует предварительную Debug-сборку и запуск из корня проекта. Внешние JSON можно скопировать в доступную для записи папку и передать их пути аргументами. Сервис читает их заново при каждом запуске, без перекомпиляции. Исходные примеры рядом с установленным приложением не считаются редактируемой рабочей БЗ.

Формат БЗ: schema_version=1, knowledge_base_id, version, synthetic, facts, rules. Признак содержит id/name/type/role; input обязательно имеет question; enum — непустой options; числа допускают min/max. Роли: input, derived, goal; пока нужен ровно один однозначный goal. Правило содержит id/title/priority/condition/conclusions/explanation/provenance. Условие — all, any либо сравнение fact_id/op/value. Операторы eq/ne совместимы со всеми типами, gt/gte/lt/lte — только с числами.

Файл исходных данных содержит schema_version=1 и массив facts с fact_id/value/origin. Только input можно задавать извне. Отсутствующий факт или null — unknown, false — известный отрицательный факт. Значение неизвестного входа при ne остается unknown. «Неприменимо» и «не задан» при предметном переносе потребуют собственных допустимых значений, не подмены null.

Числа — точно представимые decimal, integer дополнительно целый. Значения UInt64 сохраняются точно; произвольно большие числа и скрытое округление запрещены. После загрузки БЗ, факты и trace неизменяемы. Новый Run не сохраняет прежние производные. Порядок правил: больший priority, затем ordinal ID; каждое правило срабатывает максимум один раз. Разные значения одного признака вызывают конфликт, а не победу первого правила.

Коды --infer: 0 цель доказана; 1 ошибка данных/файла; 2 неверные аргументы; 3 недостаточно данных либо нет подходящего решения; 4 конфликт либо лимит. Текст разделяет эти состояния. При конфликте/лимите производные предварительные, подтвержденного итога нет. Объяснение использует фактическую трассу с источниками входов, версиями и SHA256, а не повторный вывод по измененной БЗ.

Лимиты: 1 МиБ/JSON, 128 признаков, 256 правил, 128 детей группы/заключений, 4096 узлов условий, глубина условий 16 и JSON 64, 1000 срабатываний, 10000 посещений и глубина вызовов 64 при анализе зависимостей. Текстовое раскрытие — 32 уровня и 512 узлов, структурные основания сохраняются полностью. Числовой токен — до 128 символов; экспонента -1000..1000; результат обязан точно представляться как decimal.

Анализ недостающих данных учитывает пути к цели и известные ложные ветви, но не доказывает логическую совместимость всех ограничений на неизвестные входы. Цикл без исходного основания не доказывает факт. Статическая полная непротиворечивость БЗ и предметная безопасность не заявляются.

Основание будущего предметного переноса и вопросы формализации: docs/codex/LR1_IMPORT_NOTES.md. Значение local_diagnostic остается сообщением прошивки и не становится результатом экспертного ядра автоматически.

## Шаг 04: интерфейс на C# и стиль скобок

Собственное окно и настройка приложения создаются на C#, без App.axaml и MainWindow.axaml. App.cs настраивает FluentTheme, ViewLocator и общий приемник, создает MainViewModel и MainWindow, ожидает остановку перед закрытием. Views/MainWindow.cs собирает прежний экран отдельными методами и привязывает контролы к VM через ReflectionBinding.

Главные методы окна: CreateLayout, CreateControlsPanel, CreatePortControls, CreateReplayControls, CreateReplayFileControls, CreateStatePanel, CreateObservationsPanel и CreateObservationCard. ViewModel сохраняет свойства/команды, сервисы сохраняют обработку телеметрии и знаний. C#-интерфейс не означает перенос бизнес-логики в Window.

Открывающая фигурная скобка в C# стоит на той же строке. Настройка репозитория: csharp_new_line_before_open_brace = none в корневой .editorconfig. Это смысл пользовательского «джавового стиля»; свойства/records/LINQ и именование C# остаются допустимыми. Новые окна также создавать на C#, по небольшим методам, без возвращения собственной AXAML-разметки.

--console и --infer сохраняются. Консольный опрос обязателен по методичке ЛР3, GUI с деревом — дополнительная часть. Нынешний --infer остается пакетным расчетом по файлам и еще не заменяет будущий интерактивный диалог. Предметные 20+ правил, консультация и редактор продолжаются отдельными пакетами.


## Шаг 05: предметная БЗ и ручная консультация

В Knowledge/lr1-strategies.json находятся 20 предметных правил R-01–R-20 из ЛР1 и 18 вспомогательных D-правил вычисления ПФ/оценок применимости. Их происхождение и формализация — Knowledge/RULES_CATALOG.md. Проверочные ручные входы — Scenarios/lr1-cases.json; они не являются записями ESP32.

```bash
dotnet run --project IotExpertApp.csproj -- --consult
dotnet run --project IotExpertApp.csproj -- --consult --knowledge Knowledge/lr1-strategies.json
dotnet run --project IotExpertApp.csproj -- --self-test
```

Без --knowledge читается поставляемая БЗ рядом с DLL. Для редактирования без пересборки передайте явный путь к доступной для записи копии JSON: относительный путь в примере указывает исходный файл проекта. Команда новая перечитывает этот файл и начинает сеанс заново; текущий сеанс использует закрепленную БЗ/каталог/порядок вопросов. Ошибка перезагрузки сохраняет прежний сеанс. Консольная консультация только читает файлы; редактор и сохранение рабочей копии доступны в GUI шага 07.

Оператор задает профильные сведения и готовое диагностическое заключение V1–V11. UART и local_diagnostic не преобразуются в них автоматически. Это ручной режим выбора стратегии, без отправки аппаратных команд. Вопросы задаются по еще достижимым путям; неизвестный ответ не становится нет и не повторяется автоматически.

Bool: да/нет. Enum: точный текст или номер варианта. Любой вход: не знаю, неизвестно или ? оставляет значение unknown. Неприменимо и не задан — отдельные допустимые значения соответствующих enum. Для числовых признаков используется JSON-число с точкой и общими проверками точности/диапазона.

Команды: почему — объяснить необходимость текущего вопроса; как — показать реально сработавшие правила и основания; факты — показать исходные ответы/источники; изменить <ID> <ответ> — исправить любой ручной input с полным пересчетом; новая — перезагрузить БЗ и начать сеанс; отмена/выход — завершить. Если передан --facts <файл>, он задает стартовые ручные входы и перечитывается при новой консультации.

Для штатного сценария: V1=да, V2=достаточные, V3=отсутствует, V4=без ограничений. Ожидается A1 без опроса V5–V11. После изменить V3 подтверждено прежняя рекомендация удаляется и нужны новые основания. При двух допустимых вариантах V11 определяет выбор или запрос уточнения; предпочтение не отменяет ограничения.

Каталог исходов схемы 2 различает strategy, clarification и refusal. Техническое Success означает доказанный исход консультации и не обязательно рекомендацию действия. При Conflict/StepLimit итог не подтверждается. --consult возвращает 0 при обычном выходе/отмене/EOF, 1 при начальной ошибке файла/БЗ и 2 при неверных аргументах; вид результата надо читать из текста. --infer остается отдельным пакетным режимом с прежними кодами.

На этапе 05 эти задачи оставались открыты; GUI консультации добавлен шагом 06, редактор — шагом 07, профиль актуальности и закрепление телеметрического объяснения — шагом 09. Полная v0.1.0 не объявляется завершенной.

## Шаг 06: ручная консультация в GUI

Обычный запуск dotnet run открывает окно с вкладками Монитор и Консультация (ручная). Новая консультация читает JSON БЗ схемы 2 с каталогом исходов и необязательный JSON ручных входов заново; пустой путь входов начинает опрос с начала. Техническая схема 1 сохраняется в --infer. Копию БЗ для редактирования задают явным путем в доступной для записи папке. БЗ рядом с приложением — поставляемый образец, автоматической записи в нее нет.

Ответить принимает текущее значение; варианты enum можно вводить номером или точным текстом. Не знаю сохраняет неизвестность и не задает тот же вопрос повторно. Почему показывает ограниченные возможные цепочки к цели. Для исправления выбрать ручной input, ввести значение и нажать Исправить ответ и пересчитать. Отмена блокирует ответы; прежний расчет остается только как помеченная история.

Дерево объяснения показывает закрепленную БЗ, фактическое доказательство и трассу с правилами, И/ИЛИ, значениями и происхождением. При конфликте значения предварительные, подтвержденной рекомендации нет. Циклы/глубина 32/512 узлов ограничивают отображение с видимым маркером; сам результат не меняется. Текст трассы использует прежний ExplanationService и его пределы.

Пакеты монитора продолжают обрабатываться независимо от ручной консультации и не меняют ее ответы, версию БЗ или результат. Это ручной выбор стратегии по диагностическому заключению оператора, не автоматическая диагностика платы. --consult и --infer сохраняются. ViewModel использует тот же ConsultationService, что консоль.

Монитор целиком прокручивается при небольшом окне. Успешная команда чтения/подключения снимает прежнюю локальную ошибку пути и показывает текущее сообщение приемника.

Новый self-test проверяет ViewModel и модель дерева, не запуск нативного GUI. Фактическая GUI-приемка и ограничения — docs/codex/STEP_06_RESULT.md. Редактор знаний, профиль и телеметрическая консультация остаются дальнейшими задачами.

## Шаг 07: редактор правил и рабочая копия

Вкладка База знаний загружает БЗ и создает отдельную рабочую копию. По умолчанию копия хранится в LocalApplicationData/IotExpertApp/knowledge-base.json; существующий файл не затирается. Образец рядом с DLL не редактируется. Для существующей копии укажите ее путь и нажмите Загрузить.

Выберите правило. ID существующего правила сохраняется; для нового ID используйте Новое правило. Редактируются название, приоритет Int32, объяснение и происхождение, дерево И/ИЛИ/сравнений и заключения. Bool вводится true/false, enum без кавычек, число в JSON-формате с точкой. В заключениях доступны только derived/goal. Неизвестность не является константой правила.

Применить поля к черновику проверяет полный JSON, но не пишет файл. Сохранить файл применяет оставшиеся поля и записывает проверенный документ. Удаление/примененное изменение отменяется до сохранения через Отменить изменение. Сбросить поля правила не удаляет уже примененные изменения документа; Сбросить весь черновик возвращает последнюю загруженную/сохраненную версию.

Сохранение создает резервную копию прежних байтов, пишет временный файл в той же папке и заменяет целевой файл. Внешнее изменение определяется по SHA256 и блокирует сохранение с сохранением черновика в памяти. Это оптимистическая проверка, не многопользовательская транзакция. Автоматического слияния и записи в исходную БЗ проекта нет.

Для следующих консультаций передает сохраненный путь в GUI консультации. Активный сеанс сохраняет свою версию/хеш, новую БЗ читает только Новая консультация. В консоли тот же файл задается через --consult --knowledge ПУТЬ. Пересборка для изменения правил не нужна. Форматная проверка не доказывает предметную истинность нового правила и не гарантирует отсутствие логического конфликта.

Физическая ESP32 проверяется отдельно от self-test. В отчете docs/codex/STEP_07_RESULT.md фиксируются текущие порт/device/boot/firmware/config, реальные счетчики и новый сырой захват. Наличие USB-порта само по себе не считается валидной телеметрией. Ручная консультация не получает V1–V11 из UART; отдельный автоматический сценарий шага 09 использует профиль, а local_diagnostic не определяет экспертный итог.


## Шаг 09: автоматическое состояние стенда

Выберите порт и нажмите Подключиться. Профиль DeviceProfiles/esp32-observability.json и обе внешние БЗ загрузятся автоматически; каждый принятый снимок получает оценку. Единственный USB/COM-кандидат предлагается в списке, но не открывается без команды и не объявляется ESP32 до проверки device_id/config. Чужое устройство или конфигурация дают NO_PROFILE.

Профиль контролирует свежесть esp32/oled/dht11/light/ir. Все пять свежие и ok → A1; актуальные error/unavailable при полных наблюдениях → A2; stale/disabled/not_polled/unknown → NEED_DATA. Это проектный контроль получения данных, не доказательство исправности платы. V5/V6 разрешают лишь показ оставшихся данных/ошибок; аппаратных команд и восстановления нет. PIR power_not_verified, старый тест SD, GPIO реле и передача OLED сохраняют ограничения. Быстрые изменения IR/PIR и уровни цифровых входов сами по себе не являются диагнозом.

Зафиксировать объяснение сохраняет результат выбранного снимка и трассы OBS-правил/правил ЛР1. Новые пакеты меняют текущую карточку, но не выбранный текст. Stop или просроченный live-пакет снимают текущую рекомендацию. Replay/пауза/EOF явно помечены Запись и оцениваются по временам внутри снимка, без старения по часам хоста.

Запись и воспроизведение и Технические сведения раскрываются на основной вкладке Стенд. Параметры и происхождение доступны в блоке профиля; срок 10000 мс — проектная политика актуальности, не физический порог отказа. Ошибка перезагрузки сохраняет действующий комплект/закрепленное объяснение. Для своей БЗ создайте копию профиля с корректными относительными diagnostic_knowledge/strategy_knowledge; кнопка прежнего редактора по-прежнему выбирает путь только для ручной консультации.


## Шаг 10: выборочные проверки модулей

На вкладке Стенд доступны девять карточек. Наблюдение v1, машинная проверка и ответ человека показаны раздельно. Сначала подключитесь и нажмите Получить возможности (read-only). Отправка разрешена только после валидной v1 текущего serial и версии из DeviceProfiles/selective-checks.json (начальная: lr3-2-nogit-db7e84a2a731). На старой/неизвестной прошивке запрещены все запросы, включая capabilities: прежний побайтовый протокол небезопасен для цифр JSON. В replay отправка запрещена.

Запускайте одну выбранную операцию. Для observe задайте 100…10000 мс и выполните инструкцию карточки во время окна. Ноль переходов означает только отсутствие зарегистрированных фронтов, а не отказ. Для pulse сначала явно подтвердите готовность и текущую нагрузку, затем выберите канал (фиксированные 900 мс). Разрешение сбрасывается на reconnect/boot. Выключить оба реле — отдельный явный all_off; скрытых команд при подключении/выходе нет. All_off не требует разрешения pulse и остается доступным при busy/исчерпании ID.

При потере ответа используйте Status ожидающего запроса с исходным ID, а не новый импульс. Частичная запись остается неопределенной; закрытие порта и клиентский тайм-аут не доказывают остановку на плате. Status и replayed сохраняют исходные времена. ID не переиспользуются для другого содержимого, переполнения в ноль нет.

Раскройте Выборочная проверка и ответы человека, выберите результат и при необходимости закрепите его. Да/Нет/Неясно/Не проверял относятся к конкретным device/boot/request/source, сохраняются со способом и временем наблюдения, не отправляются в прошивку и не меняют v1/OBS/ЛР1. Отсутствие ответа отдельно от Нет. История ограничена 64 результатами и 128 ответами; Сохранить протокол в JSON открывает выбор пользовательского файла. Автосохранения в установленный каталог и новой БД нет.

Автоматическое объяснение фиксируется отдельно от выборочного теста: итог, снимок, наблюдения, дерево OBS, переход к входам ЛР1 и дерево стратегии. Хеши/полная трасса раскрываются отдельно. Исходная общая БЗ и пять обязательных источников не расширены. Initialized и completed не доказывают физическую исправность, передача OLED не доказывает видимость, GPIO реле — контакты, heap — свободное место SD.


## Шаг 11: главная карточка и управляемые проверки

На вкладке «Стенд» порт, автоматический A*, загруженный профиль/версии трех БЗ и сводка проверок находятся в одной карточке. Девять плиток перестраиваются в 3/2/1 столбец; область выбранной проверки находится рядом либо ниже. Техническая история, пути, хеши, replay и объяснение A* раскрываются отдельно. Ручная консультация и редактор сохранены.

«Проверить» выбирает модуль и показывает инструкцию. Отдельная кнопка запускает операцию. Срок ответа — целое 5…300 с, по умолчанию 30; «Сохранить срок» записывает только пользовательскую настройку. На macOS файл находится в `~/Library/Application Support/IotExpertApp/check-preferences.json` (на других ОС — LocalApplicationData/IotExpertApp). Значение и БЗ закрепляются на старте, изменение поля не сдвигает текущий deadline.

У OLED вопрос открывается после ready, у GPIO/реле — после завершенного окна/импульса. «Да», «Нет», «Неясно», «Пропустить» и отсутствие ответа различаются. Timeout не создает HumanCheckAnswer. RAM/DHT/SD не требуют ответа. OLED получает один адресный finish после ответа/срока; только terminal с данными подтверждает восстановление. При потере ответа используйте status исходного ID и при необходимости явное завершение, без нового рисунка. Stop/Close дают существующему worker до 600 мс на best-effort finish; при отсутствии подтверждения действует конечный watchdog, восстановление не обещается.

DeviceProfiles/selective-checks.json явно разрешает `lr3-2-nogit-db7e84a2a731` → protocol 1 и `lr3-3-nogit-9d4af0c663d9` → protocol 2, только для указанного device/config. После совместимой v1 новая версия получает один автоматический capabilities. На старой прошивке удерживаемый OLED недоступен; старый TEST_EVENT v1 сохраняет строгий разбор. Неизвестная прошивка/replay не разрешают запись. Новые примеры `CheckExamples/interactive-oled-synthetic.jsonl` синтетические.

Вывод конкретной проверки выполняет прежний движок по внешней `DeviceProfiles/esp32-module-checks.rules.json` (esp32-module-checks / module-feedback-1, 19 правил MOD). Необязательная ссылка `module_check_knowledge` загружается атомарно с профилем: ошибка оставляет прежний комплект, старый профиль показывает отсутствие расширения. Реальные факты, правила и версия доступны в «Почему?», JSON-экспорте. Смысл заключений:

| Доказательства | Заключение модуля |
|---|---|
| Подтвержденная машинная ошибка | «Ошибка машинной проверки» с причиной и пределами; ответ «Да» ее не отменяет |
| Явный отказ запроса до исполнения | «Проверка не выполнена»; не «модуль сломан» |
| Источник/boot потерян или отправка неопределенна | «Проверка прервана / исход неизвестен»; не физический PASS |
| Нужен человек, срок истек | «Не подтверждено: ответ не получен за N с» |
| Нужен человек, явный пропуск | «Пользователь не проверял» |
| Нужен человек, Неясно | «Нужна повторная проверка: ответ неясен» |
| OLED передан, штатный экран восстановлен, человек ответил «Да» | «Отображение тестового рисунка подтверждено пользователем» |
| OLED передан, человек ответил «Нет» | «Передача выполнена, ожидаемое изображение пользователь не подтвердил»; не выдумывать причину неисправности |
| Pulse завершен и возврат подтвержден, человек ответил «Да» | «Программный импульс и слышимый отклик подтверждены в пределах теста»; контакты/нагрузка не измерены |
| Pulse завершен, человек ответил «Нет» | «Программный импульс завершен, щелчок не подтвержден»; не равняется измерению контактов |
| GPIO-окно имеет переходы и человек ответил «Да» | «Реакция входа наблюдалась в этом окне»; для PIR обязательно «питание отдельно не подтверждено» |
| GPIO-окно без переходов, человек ответил «Нет» | «В окне реакция не зарегистрирована и не подтверждена»; это не диагноз поломки |
| Человек ответил «Да» без зарегистрированных переходов либо человек ответил «Нет» при переходах | «Наблюдение пользователя и зарегистрированный сигнал расходятся; нужна повторная проверка» |
| Успешный snapshot/read_next/SD без вопроса | Узкое заключение: «Метрики получены» / «Новое чтение получено» / «Файловый тест завершен, очистка подтверждена» |
| Неизвестная причина/неполные данные | «Недостаточно оснований для заключения» |

Общий A* по OBS/ЛР1 сохраняет прежний смысл; ответы человека не меняют v1.status или V2–V4. Сводка рядом показывает подтверждения, замечания и отсутствие ответа. При Stop/replay/другом boot итог помечается историей. Реле требует отдельного разрешения и клика на 900 мс; all_off снимает queued pulse, сохраняет бронь ID и не снимает отправленный/неопределенный pending без terminal/status. Эти правила не измеряют контакты, питание PIR или емкость SD.

Фактические проверки, ограничения аппаратной приемки и снимки: `docs/codex/STEP_11_RESULT.md`, `docs/codex/checks/step11/`. Полная версия v0.1.0 этим пакетом не объявляется принятой.
