# IotExpertApp

Приложение для ЛР3 ИИСиТ. Есть приемник телеметрии ESP32 с монитором, записью и replay, а также техническое ядро прямого вывода по внешним JSON. Предметная БЗ и полноценная консультация еще не завершены.

## Запуск

Из каталога с IotExpertApp.csproj:

```bash
dotnet restore IotExpertApp.csproj
dotnet build IotExpertApp.csproj
dotnet run --project IotExpertApp.csproj
dotnet run --project IotExpertApp.csproj -- --self-test
dotnet run --project IotExpertApp.csproj -- --write-synthetic-sample synthetic-uart.log
dotnet run --project IotExpertApp.csproj -- --console --file synthetic-uart.log
```

Консоль с реальной платой:

```bash
dotnet run --project IotExpertApp.csproj -- --console --port /dev/cu.ИМЯ_ПОРТА
```

Имя заменить на обнаруженный порт; на Windows используется имя COM. Параметры: 115200, 8N1, без flow control. Serial monitor другой программы должен освободить порт. GUI и CLI одновременно один порт не открывают. DTR/RTS не используются для преднамеренного сброса; фактический reset при открытии обрабатывается как новый boot.

На Windows OutputType=Exe нужен для консольного режима; при запуске GUI может появляться консольное окно. Скрытие окна при сохранении полноценного CLI — отдельная упаковочная задача.

## Сборка с --no-restore

В текущем csproj пакет AvaloniaUI.DiagnosticsSupport исключен из assets вне Debug. Файл obj/project.assets.json общий для конфигураций, поэтому после Release-restore Debug-сборка с --no-restore может выдать CS1061 для WithDeveloperTools. Это не ошибка using: сначала нужно восстановить пакеты для выбранной конфигурации.

```bash
dotnet restore IotExpertApp.csproj -p:Configuration=Debug
dotnet build --no-restore --tl:off
```

Для Release:

```bash
dotnet restore IotExpertApp.csproj -p:Configuration=Release
dotnet build -c Release --no-restore --tl:off
```

При смене конфигурации повторить соответствующий restore либо использовать обычный dotnet build без --no-restore. Вызов WithDeveloperTools остается только под #if DEBUG; менять код или версии пакетов для этой ситуации не требуется.

## Работа

В GUI выбрать порт и подключиться либо указать абсолютный путь UART-записи. Остановить прием можно кнопкой. Файл читается быстро либо по времени с паузой; режим выбирается перед запуском. Путь выбирается текстовым полем; файловый диалог будет последующим улучшением.

Модели пакета и наблюдений не являются сущностями ORM. ObservationStore хранит один текущий снимок. TelemetryReceiverService координирует источник, сборку строк, парсер и хранилище. MainViewModel получает сервис через конструктор и обновляет свойства интерфейса на UI-потоке. App создает зависимости и останавливает прием перед закрытием окна.

Синтетическая запись создается только командой --write-synthetic-sample; это не измерения платы. --self-test проверяет части приемника на искусственных входах. Консольный приемник возвращает ненулевой код при ошибке формата, порядка, хвосте, ошибке источника или отсутствии валидных пакетов.

## Текущие ограничения

- Поддерживается schema_version=1 и профиль stand-v1-pir-unverified; несовместимые пакеты отклоняются с сообщением.
- Возраст отображается на момент снимка, не как непрерывно растущий срок годности.
- Последняя успешная величина не подменяет ошибку последней попытки.
- PIR не подтверждает движение, OLED не подтверждает картинку, SD — только стартовый тест, реле — GPIO без обратной связи контактов.
- local_diagnostic показывается как локальное заключение прошивки, не результат экспертной системы приложения.
- Есть контроль sequence/uptime и согласованности времен/счетчиков источников; он обнаруживает противоречия наблюдениям, а не физическую причину неисправности.
- Предметная БЗ из 20+ правил, интерактивная консультация, GUI дерева и редактор еще не реализованы; техническое ядро на искусственных правилах не равно завершенной v0.1.0.

Полный объем версии: docs/codex/LR3_APP_v0.1.0_SPEC.md. Ожидаемые и фактически пройденные проверки разделяются в отчете Codex.



## Шаг 02: запись и воспроизведение

При подключении к UART можно указать новый абсолютный путь в поле записи. Пустое поле отключает запись. Существующие файлы не затираются. Записываются исходные байты до разбора: загрузочные логи, правильные и поврежденные JSON-строки. Заголовки, BOM и переводы строк от приложения не добавляются. Ошибка записи не прекращает прием и отображается отдельно.

Лимит одного файла — 10 МиБ. При нехватке места для очередного блока запись останавливается перед ним, а прием продолжается. Кнопка «Завершить запись» закрывает файл и не отключает порт. Файл может закончиться неполным кадром при остановке/лимите; хвост учитывается при replay, а не дополняется автоматически. Это запись доступного приложению потока, а не гарантия отсутствия потерь до UART-драйвера. Запись не обязана начинаться с sequence=0.

Новая команда для реального порта, имя заменить на подтвержденное имя ESP32:

```bash
dotnet run --project IotExpertApp.csproj -- --console --port /dev/cu.usbserial-0001 --record /АБСОЛЮТНЫЙ/НОВЫЙ/esp32-real.log --seconds 30
```

Каталог файла должен существовать. --seconds принимает от 1 до 300, после интервала выполняется штатный Stop. Без ограничения времени CLI завершается по Ctrl+C. GUI и CLI не открывают один порт одновременно.

```bash
dotnet run --project IotExpertApp.csproj -- --console --file /АБСОЛЮТНЫЙ/esp32-real.log
dotnet run --project IotExpertApp.csproj -- --console --file /АБСОЛЮТНЫЙ/esp32-real.log --timed
```

В GUI флажок «Воспроизводить по времени» применяется при запуске файла. Пауза/продолжение действуют только на replay. «Остановить» завершает чтение, повторное «Прочитать файл» начинает его сначала. Быстрый режим не делает ожиданий. Живой UART не ставится на паузу этой кнопкой.

Интервалы определяются uptime между принятыми пакетами одного запуска, а не датой компьютера. Первый пакет показывается сразу, новый boot начинает отдельную шкалу времени. Пауза замораживает часы записи; EOF не оставляет фонового отсчета. У текстовых строк нет собственного времени, они обрабатываются между соседними пакетами. Виртуальный uptime отображается отдельно; возраст в карточках по-прежнему указан на момент снимка. Вывод о годности данных и экспертные пороги здесь не добавлены.

Межпакетная проверка не допускает уменьшения времен/числа попыток и изменения values без нового времени успеха. При одной новой ошибке сохраняется прошлый успех. При нескольких попытках допускаются пропущенные промежуточные успехи/ошибки; при насыщении счетчика не предполагается точное число попыток. Несогласованный пакет не заменяет снимок и считается отдельно от ошибки JSON.

«Пропуски» означают промежуток между номерами принятых пакетов: причиной может быть как потеря, так и отклонение пакета валидатором. Счетчик не определяет физическую причину.

Проверки --self-test дополнены искусственными переходами наблюдений, точной записью байтов, запретом перезаписи, лимитом, паузой и остановкой replay. Они не являются проверкой физической ESP32. Фактические аппаратные результаты сохраняются отдельно в docs/codex/STEP_02_RESULT.md вместе с реальной записью.

## Шаг 03: техническое ядро внешней БЗ

Это проверка алгоритма по искусственным данным, не диагноз ESP32. Четыре правила SYN-* не входят в минимум двадцати предметных правил. Полноценный диалог, маппинг телеметрии и GUI консультации будут отдельными этапами.

```bash
dotnet run --project IotExpertApp.csproj -- --infer --knowledge KnowledgeExamples/synthetic-engine.json --facts KnowledgeExamples/synthetic-facts.json
dotnet run --project IotExpertApp.csproj -- --self-test
python3 docs/codex/checks/step03/verify_knowledge_cli.py
```

Последняя команда требует предварительную Debug-сборку и запуск из корня проекта. Внешние JSON можно скопировать в доступную для записи папку и передать их пути аргументами. Сервис читает их заново при каждом запуске, без перекомпиляции. Исходные примеры рядом с установленным приложением не считаются редактируемой рабочей БЗ.

Формат БЗ: schema_version=1, knowledge_base_id, version, synthetic, facts, rules. Признак содержит id/name/type/role; input обязательно имеет question; enum — непустой options; числа допускают min/max. Роли: input, derived, goal; пока нужен ровно один однозначный goal. Правило содержит id/title/priority/condition/conclusions/explanation/provenance. Условие — all, any либо сравнение fact_id/op/value. Операторы eq/ne совместимы со всеми типами, gt/gte/lt/lte — только с числами.

Файл исходных данных содержит schema_version=1 и массив facts с fact_id/value/origin. Только input можно задавать извне. Отсутствующий факт или null — unknown, false — известный отрицательный факт. Значение неизвестного входа при ne остается unknown. «Неприменимо» и «не задан» при предметном переносе потребуют собственных допустимых значений, не подмены null.

Числа — точно представимые decimal, integer дополнительно целый. Значения UInt64 сохраняются точно; произвольно большие числа и скрытое округление запрещены. После загрузки БЗ, факты и trace неизменяемы. Новый Run не сохраняет прежние производные. Порядок правил: больший priority, затем ordinal ID; каждое правило срабатывает максимум один раз. Разные значения одного признака вызывают конфликт, а не победу первого правила.

Коды --infer: 0 цель доказана; 1 ошибка данных/файла; 2 неверные аргументы; 3 недостаточно данных либо нет подходящего решения; 4 конфликт либо лимит. Текст разделяет эти состояния. При конфликте/лимите производные предварительные, подтвержденного итога нет. Объяснение использует фактическую трассу с источниками входов, версиями и SHA256, а не повторный вывод по измененной БЗ.

Лимиты: 1 МиБ/JSON, 128 признаков, 256 правил, 128 детей группы/заключений, 4096 узлов условий, глубина условий 16 и JSON 64, 1000 срабатываний, 10000 посещений и глубина вызовов 64 при анализе зависимостей. Текстовое раскрытие — 32 уровня и 512 узлов, структурные основания сохраняются полностью. Числовой токен — до 128 символов; экспонента -1000..1000; результат обязан точно представляться как decimal.

Анализ недостающих данных учитывает пути к цели и известные ложные ветви, но не доказывает логическую совместимость всех ограничений на неизвестные входы. Цикл без исходного основания не доказывает факт. Статическая полная непротиворечивость БЗ и предметная безопасность не заявляются.

Основание будущего предметного переноса и вопросы формализации: docs/codex/LR1_IMPORT_NOTES.md. Значение local_diagnostic остается сообщением прошивки и не становится результатом экспертного ядра автоматически.

## Шаг 04: интерфейс на C# и стиль скобок

Собственное окно и настройка приложения создаются на C#, без App.axaml и MainWindow.axaml. App.cs настраивает FluentTheme, ViewLocator и общий приемник, создает MainViewModel и MainWindow, ожидает остановку перед закрытием. Views/MainWindow.cs собирает прежний экран отдельными методами и привязывает контролы к VM через ReflectionBinding.

Главные методы окна: CreateLayout, CreateControlsPanel, CreatePortControls, CreateReplayControls, CreateReplayFileControls, CreateStatePanel, CreateObservationsPanel и CreateObservationCard. ViewModel сохраняет свойства/команды, сервисы сохраняют обработку телеметрии и знаний. C#-интерфейс не означает перенос бизнес-логики в Window.

Открывающая фигурная скобка в C# стоит на той же строке. Настройка репозитория: csharp_new_line_before_open_brace = none в корневой .editorconfig. Это смысл пользовательского «джавового стиля»; свойства/records/LINQ и именование C# остаются допустимыми. Новые окна также создавать на C#, по небольшим методам, без возвращения собственной AXAML-разметки.

--console и --infer сохраняются. Консольный опрос обязателен по методичке ЛР3, GUI с деревом — дополнительная часть. Нынешний --infer остается пакетным расчетом по файлам и еще не заменяет будущий интерактивный диалог. Предметные 20+ правил, консультация и редактор продолжаются отдельными пакетами.
